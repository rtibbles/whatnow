# WhatNow Database Migrations

This directory contains Alembic database migrations for WhatNow.

## Overview

Alembic is used to manage database schema changes safely and reversibly. Migrations are automatically applied when the app starts.

## Directory Structure

```
alembic/
├── README.md           # This file
├── env.py              # Alembic environment configuration
├── script.py.mako      # Template for new migrations
└── versions/           # Migration scripts
    └── 20251113_0000_initial_schema.py  # Initial baseline
```

## Automatic Migrations

**For Users:**
Migrations run automatically when you start WhatNow. You don't need to do anything.

**For Developers:**
When you modify models in `whatnow/models.py`, you need to create a migration.

## Creating a New Migration

### Method 1: Autogenerate (Recommended)

1. Modify the models in `whatnow/models.py`
2. Generate migration automatically:
   ```bash
   cd /path/to/whatnow
   alembic revision --autogenerate -m "Add new column to pings"
   ```
3. Review the generated migration in `alembic/versions/`
4. Test the migration:
   ```bash
   alembic upgrade head
   alembic downgrade -1
   alembic upgrade head
   ```

### Method 2: Manual Migration

1. Create empty migration:
   ```bash
   alembic revision -m "Descriptive message"
   ```
2. Edit the generated file in `alembic/versions/`
3. Fill in the `upgrade()` and `downgrade()` functions
4. Test as above


### Downgrade one version
```bash

```

### Upgrade/downgrade to specific version
```bash

alembic downgrade 001_initial
```

## SQLite Considerations

WhatNow uses SQLite, which has limited ALTER TABLE support. Alembic is configured with `render_as_batch=True` to work around these limitations.

**Important:** Test migrations thoroughly on a copy of your database before deploying!

## Migration Best Practices

1. **Always test migrations**
   - Create a backup of your database first
   - Test upgrade AND downgrade paths
   - Verify data integrity after migration

2. **Keep migrations small**
   - One logical change per migration
   - Easier to review and debug
   - Easier to roll back if needed

3. **Review autogenerated migrations**
   - Alembic might miss some changes
   - Check for unintended modifications
   - Add data migrations if needed

4. **Write reversible migrations**
   - Always implement `downgrade()`
   - Consider data loss implications
   - Document irreversible changes

5. **Test with existing data**
   - Migrations should handle existing records
   - Consider default values for new columns
   - Handle nullable vs non-nullable carefully

## Example Migration

```python
"""Add priority to local todos

Revision ID: 002_add_priority
Revises: 001_initial
Create Date: 2025-11-13 10:00:00.000000
"""
from alembic import op
import sqlalchemy as sa

revision = '002_add_priority'
down_revision = '001_initial'

def upgrade() -> None:
    # Add priority column with default value
    with op.batch_alter_table('local_todos') as batch_op:
        batch_op.add_column(
            sa.Column('priority', sa.Integer(), nullable=False, server_default='0')
        )

def downgrade() -> None:
    # Remove priority column
    with op.batch_alter_table('local_todos') as batch_op:
        batch_op.drop_column('priority')
```

## Troubleshooting

### Migration fails with "table already exists"

This usually means the migration was partially applied. Options:
1. Use `alembic stamp head` to mark current state
2. Manually fix the database and migration
3. Start fresh with a backup

### Autogenerate doesn't detect changes

- Ensure models are imported in `env.py`
- Check that Base.metadata includes your models
- Some changes (like indexes) may need manual migrations

### SQLite "Cannot add NOT NULL column"

SQLite doesn't support adding NOT NULL columns to existing tables easily. Options:
1. Add column as nullable first, then add NOT NULL constraint
2. Use batch operations in migration
3. Provide server_default value
